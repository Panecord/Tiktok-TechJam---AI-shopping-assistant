## Ground rules (non-negotiable — from `.github/skills/shopping-copilot-dev/SKILL.md` and
`references/technical-spec.md`)

1. Scope is fixed to `starter/agent.py` (plus tests, plus the hygiene fixes in Task 0
   below). Never edit `evaluator/local_evaluator.py` or `data/public_set.jsonl`.
2. Never return a `parent_asin` outside the frozen catalog. LLM rerank output is
   validated against the candidate pool; invalid → retry once → fall back to the
   deterministic top candidate.
3. `ask_attribute` must be one of: `category, material, color, size, style, brand,
   budget, feature, use_case, other, null`.
4. The ask-vs-recommend decision stays a **fixed deterministic rule** (pool size +
   score margin threshold). No learned/RL policy for this decision, ever.
5. Turn budget: by turn 9 the agent must force a recommendation. No session may exceed
   10 turns.
6. No new abstractions, plugin systems, or "for extensibility" layers. No external
   vector DB, no fine-tuning, no catalog mutation.
7. `usage.prompt_tokens` / `completion_tokens` must be real counts, never placeholders.
8. Never commit API keys/credentials.
9. Tune thresholds/weights only against `data/public_set.jsonl`. Log what changed and
   the resulting metric shift for every tuning pass. If a tuning pass doesn't clearly
   improve a metric, revert it — don't stack unverified changes.

Source of truth for architecture/history: `IMPROVED_AGENT_README.md` (now at v2.8.0 —
this is the current authoritative doc, **not** the stale root-level `README.md`, see
Task 0.5). Keep it updated with every version bump, same format as the existing rows.

## Task 11 — Re-validate the LLM rerank with `recent_turns` (parallelized runner)

`recent_turns` was added to the `_call_llm_rerank` prompt in v2.8.0 (this was the fix
Task 6 called for), but `_validate_llm.py` has not been re-run since — `validation_llm.json`
still reflects the pre-fix prompt (HR `0.555`, MRR `0.3557`, score `0.4417`, 206 LLM
calls). The prior full 200-session run took ~5300s (~88 min) sequentially, which is
part of why it hasn't been re-run. Two things to do here, in order:

**11.1 Speed up `_validate_llm.py` before re-running it at full scale.**
The script (`_validate_llm.py:62-87`) runs all 200 sessions strictly sequentially, one
`evaluate(agent, [sample], ...)` call at a time, reusing one `Agent` instance. Back-of-
envelope: ~5300s / ~260 total LLM calls (1.3/session × 200) ≈ 20s/call, far above the
observed healthy 4-6s latency — so the time is very likely dominated by LLM network
wait (throttling and/or calls stalling near the 30s timeout before falling back), not
local retrieval computation (already optimized via the posting-list index).
- **Confirm first:** add a quick per-session timing split (time inside
  `_call_llm_rerank` vs. everything else) to the existing progress logging in
  `_validate_llm.py`, run ~20 sessions, and confirm LLM-call time really is the
  dominant term before investing further.
- **Parallelize across sessions.** Sessions are independent (`evaluate()` calls
  `agent.reset(session_id, ...)` per sample, and dialogue state lives in
  `self._sessions[session_id]` — see `agent.py:1028` — so different sessions don't
  collide on state). Use `concurrent.futures.ThreadPoolExecutor` (the dominant cost is
  network I/O, which releases the GIL, so threads are sufficient — no need for
  multiprocessing). **Important:** do not share one `Agent` instance across concurrent
  threads — `_last_candidates` (`agent.py:782`) is a plain, un-namespaced instance
  attribute, and the spec explicitly disclaims multi-session concurrency safety
  (`technical-spec.md` §7). Give each worker its own `Agent` instance built once at
  worker start, split the 200 samples into N slices, and merge each worker's
  hit/MRR/token totals at the end (plain summation — no locking needed, since merging
  only happens once all workers finish their slice).
- Start with a modest worker count (4-8) — push higher only if it keeps helping;
  DeepSeek's own rate limiting is the real ceiling, and over-parallelizing just
  produces more throttled/timed-out calls.
- Optionally reuse HTTP connections per worker (`_call_llm_rerank` opens a fresh
  `urllib.request.urlopen` per call) for a smaller additional win — secondary to the
  concurrency change.

**11.2 Re-run and record the result.**
- First run a ~40-session stratified sample (covering all 4 scenario types
  proportionally) to sanity-check that `recent_turns` actually improved MRR over the
  stale `0.3557` baseline before committing to a full run.
- If it looks better, run the full 200-session set with the parallelized script and
  overwrite `validation_llm.json`.
- Either way, record the honest result: if MRR still doesn't clearly beat the
  deterministic path (`0.4787` in the current v2.8.0 default), say so plainly in §9
  Limitations rather than changing default behavior — `use_llm` stays recommend-branch-
  only, off by default, per rule 4.
- The other five `validation_*.json` diagnostic files are also stale (predate the
  materials-vocab/v2.7.0/v2.8.0 work) — re-running them is not required for this task,
  just don't treat their numbers as current.

## Task 12 — Find the real ceiling, then A/B the embedding dense-retrieval path

**Why this task exists:** the scoring formula (`0.5·HR@10 + 0.3·MRR + 0.2·Efficiency`)
means MRR and Efficiency are now tightly coupled to HR@10 — a session can't earn MRR
without being a hit, and the current MRR/HR ratio (`0.4787/0.650 ≈ 0.74`) shows hits are
already ranked close to #1 on average. There's little headroom left in "rank hits
better"; the score now moves almost entirely with **how many sessions hit at all**.
Concretely: holding current ratios roughly constant, a technical score of `0.70`
requires **HR@10 ≈ 0.81** — a +16-point jump from the current `0.650`. Tasks 3/7/8/9
are precision-refinement on an already-decent reranker and will not deliver that alone
(realistically a few points each, stacking to maybe `0.60-0.63` score). Something
structurally bigger is needed if `0.70` is the real target. **If a score of ~0.7 is the
actual goal, treat this task as higher priority than Task 3.**

**12.1 Re-check the real ceiling first.** `_validate_pool_recall.py`'s last recorded
number (pool recall `0.960`, i.e. the target is somewhere in the fused candidate pool
96% of the time) is from v2.6.0 and is now stale relative to all the retrieval/slot
changes since. Re-run it. If pool recall has held or improved, HR@10 `0.81` is at least
retrieval-reachable and the bottleneck is genuinely reranking/selection. If it's dropped
meaningfully, retrieval itself is now the ceiling and no amount of reranker tuning will
reach `0.81` — that changes what to prioritize.

**12.2 A/B the already-built sentence-embedding dense retrieval path.**
`starter/agent.py` has a second, pretrained sentence-embedding retrieval path (v2.3.0,
inference-only, no fine-tuning — fully in scope) sitting unused behind
`COPILOT_DENSE=embed`; the default is still the lexical TF-IDF fallback.
TF-IDF is structurally incapable of the "emerald ≈ green" type matches Task 3 tries to
patch by hand with a synonym dict — a real embedding model captures that natively in
the representation itself, and would likely subsume most of Task 3's benefit plus more.
Its last A/B (`validation_embed.json`) is stale and predates this entire round of
fixes.
- Re-run `_validate_embed.py` (fix its path if still needed, same pattern as Task 0.3)
  against the **current** pipeline (post materials-vocab, post ask-attribute-
  reachability, post `recent_turns`), full 200-session set.
- Compare HR@10/MRR/MTTC/score directly against the current TF-IDF default.
- If embeddings clearly win, make `COPILOT_DENSE=embed` the default (flag the added
  cost honestly: a model download/load at startup, slower per-turn encode than TF-IDF —
  note this trade-off in the README rather than hiding it). If they don't clearly win,
  keep TF-IDF as default and record the finding — don't force a switch that doesn't pay
  off, same rule as every other tuning pass in this plan.
- This task can run independently of / in parallel with Task 3 — if embeddings turn out
  to subsume the synonym problem, Task 3 may become unnecessary; decide after seeing
  the A/B, not before.
