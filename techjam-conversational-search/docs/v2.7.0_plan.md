# Track 4 Shopping Copilot — v2.7.0 Implementation Plan (handoff doc)

Give this whole file to the coding agent. Work top to bottom, **one numbered task at a
time**: finish a task, run the relevant check, report what changed and the metric delta
(if any), then stop and wait before starting the next one. Do not batch tasks.

## Ground rules (non-negotiable — from `.github/skills/shopping-copilot-dev/SKILL.md` and
`references/technical-spec.md`)

1. Scope is fixed to `starter/agent.py` (plus tests, plus the hygiene fixes in Task 0
   below). Never edit `evaluator/local_evaluator.py` or `data/public_set.jsonl`.
2. Never return a `parent_asin` outside the frozen catalog. LLM rerank output is
   validated against the candidate pool; invalid → retry once → fall back to the
   deterministic top candidate.
3. `ask_attribute` must be one of: `category, material, color, size, style, brand,
   budget, feature, use_case, other, null`.
4. The ask-vs-recommend decision stays a **fixed deterministic rule** (pool size +
   score margin threshold). No learned/RL policy for this decision, ever.
5. Turn budget: by turn 9 the agent must force a recommendation. No session may exceed
   10 turns.
6. No new abstractions, plugin systems, or "for extensibility" layers. No external
   vector DB, no fine-tuning, no catalog mutation.
7. `usage.prompt_tokens` / `completion_tokens` must be real counts, never placeholders.
8. Never commit API keys/credentials.
9. Tune thresholds/weights only against `data/public_set.jsonl`. Log what changed and
   the resulting metric shift for every tuning pass. If a tuning pass doesn't clearly
   improve a metric, revert it — don't stack unverified changes.

Source of truth for architecture/history: `IMPROVED_AGENT_README.md` (v2.6.0 — this is
the current authoritative doc, **not** the stale root-level `README.md`, see Task 0.5).

## Task 2 — Priority framing: fix ranking, not retrieval

`IMPROVED_AGENT_README.md` §"v2.6.0" already instrumented this: **pool recall is
`0.960`** (the target is in the fused candidate pool 96% of the time) but **Hit
Rate@10 is only `0.545`** (it's only in the top-10 after reranking half the time). The
bottleneck is entirely in ranking/selection, not in what retrieval finds. Every task
below (3-6) targets ranking precision. Do **not** widen `BM25_TOP`/`DENSE_TOP` or add
new retrieval signals as a v2.7.0 task — that has already been shown not to be the
lever that matters.

---

## Task 3 — Synonym-aware slot matching (limitation: lexical-only attribute matching)

`IMPROVED_AGENT_README.md` §9 flags: "the deterministic reranker uses lexical
attribute matching, so subtle synonyms may be missed" (see `_slot_match_score` in
`starter/agent.py`). Add a small **static** synonym/normalization table for the
highest-value attributes (color, material — check `data/public_set.jsonl` for the most
common mismatches first, e.g. "navy" vs "blue", "cotton blend" vs "cotton"). This must
stay a deterministic lookup table, not a learned or embedding-based similarity — that
would be a new abstraction beyond the spec.
- **Test:** a session where the target's attribute is a synonym of what the slot text
  literally contains; confirm `_slot_match_score` now scores it correctly and the
  session still passes existing regression tests in `test_pivot_slots.py` /
  `test_buying_regression.py`.
- Re-run the evaluator, record the HR@10/MRR delta.

## Task 4 — Category detection beyond the fixed token list

`IMPROVED_AGENT_README.md` §9: "Category detection relies on a fixed token list; rare

## Task 5 — Define null-price budget-matching behavior

`IMPROVED_AGENT_README.md` §9: "Budget matching only applies when a product has a

null-price products (e.g., neutral mid-score instead of an implicit 0, or excluded
from the budget dimension of scoring but still eligible via other signals) — pick
whichever doesn't regress Buying-scenario HR, and document the rationale in a comment.
- **Test:** both branches — a null-price product with a budget slot set, and the
  existing non-null-price path unchanged.
- Re-run evaluator, record delta, especially the Buying-scenario breakout.

## Task 6 — Investigate the LLM rerank underperformance

`validation_llm.json` (from `_validate_llm.py`, DeepSeek `deepseek-v4-flash`, all 200
sessions) shows the LLM-enabled path scoring **worse** than the deterministic path:
HR `0.555` / MRR `0.3557` / score `0.4417`, vs. deterministic v2.6.0's HR `0.545` /
MRR `0.4226` / score `0.4542`. Since HR is actually similar but MRR drops
meaningfully, the LLM is likely getting the target *into* top-10 about as often but
ranking it lower within it.
- Check `_call_llm_rerank` (`starter/agent.py` ~lines 788-843) against the spec's
  documented rerank request shape (`technical-spec.md` §2: `{candidate_ids,
  slot_state, recent_turns}`) — confirm `slot_state` and `recent_turns` are actually
  being included in the prompt, not just `candidate_ids` + title snippets. Missing
  context is the most likely cause of a relevance-plausible-but-not-optimal ordering.
- If context is missing, add it to the prompt (keep prompt size bounded —
  `LLM_TOP = 25` candidates is already the cap).
- Re-run `_validate_llm.py` (after Task 0.3's path fix) to get fresh
  `validation_llm.json` numbers. This is a real network call against DeepSeek and
  takes ~100 minutes for all 200 sessions per the prior run — confirm with the
  operator before running the full set; a smaller sample (e.g. first 40 sessions) is
  fine for a first pass.
- If MRR still doesn't beat deterministic after adding context, that is an acceptable
  documented finding, not something to force — keep `use_llm` gating exactly as-is
  (recommend-branch only, off by default) and record the result honestly in the
  README's limitations section rather than changing default behavior.
